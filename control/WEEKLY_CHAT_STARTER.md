# Стартовый файл недельного чата ROS2-AMR

> Вставь этот блок в начало нового чата перед задачами недели N.

## 1. Роли
- **Ты (пользователь):** исполнитель, заказчик, тестировщик, автор документов.
- **AI:** куратор задачи. Не правит файлы самостоятельно, но пишет код в чате с объяснениями, дает exact patch по запросу, находит несостыковки.

## 2. Структура недели

### Понедельник — Железный аудит и инфраструктура
**Что делаем:** проверяем компоненты, порты, питание, Docker, сборку.

**Обоснование для TeamLead:** любой спринт в embedded/робототехнике начинается с аудита ресурсов. Пропуск этого шага приводит к срыву сроков на 3–5 дней из-за неожиданных hardware-проблем.

**Пример из практики:** на Week 3 выяснилось, что WEMOS Motor Shield не отвечает по I2C. Если бы аудит был в первый день, 3 дня диагностики сократились бы до нескольких часов.

### Вторник–четверг — Разработка и отладка
**Что делаем:** пишем код, конфиги, прошивку. Начинаем с mock-режима, затем переходим на железо.

**Обоснование для TeamLead:** mock-режим развязывает software и hardware команды. Пока одна часть команды ждет железо, другая продолжает разработку.

**Пример из практики:** пока заказывался новый ESP32-DevKitC, software-команда могла тестировать serial_bridge в mock-режиме и не простаивать.

### Пятница — Интеграционное тестирование
**Что делаем:** собираем все подсистемы в единый pipeline, проводим end-to-end тест.

**Обоснование для TeamLead:** интеграция — самый рискованный этап. Регулярная пятничная интеграция позволяет находить проблемы до финального дедлайна.

**Пример из практики:** интеграция teleop + serial_bridge + ESP32 выявила рассогласование топиков `/cmd_vel` и `/amr/cmd_vel`, которое было бы критичным на демо.

### Суббота–воскресенье — Документация, code review, merge
**Что делаем:** обновляем документы, проводим review, сливаем ветку в `main`, пишем ретроспективу.

**Обоснование для TeamLead:** документация и review — не формальность, а страховка от потери знаний и технического долга. Команда из 10+ человек без документации превращается в хаос.

**Пример из практики:** `docs/TROUBLESHOOTING.md` с фиксацией проблемы Docker Hub позволил бы новому разработчику не повторять чужие ошибки.

## 3. Правила для AI

### Перед каждой задачей
- Проверить `git status`, текущую ветку, последние коммиты.
- Проверить наличие и версии ключевых файлов.

### Железо — первым делом
- `ls /dev/ttyUSB*` — какие устройства подключены.
- `ros2 topic hz /scan` — лидар публикует данные.
- `pio device list` — ESP32 виден PlatformIO.

**Обоснование для TeamLead:** диагностика железа должна быть стандартизирована. Если каждый разработчик проверяет по-своему, часть информации теряется.

**Пример из практики:** стандартный чек-лист диагностики RPLIDAR (порт, baud, вращение) сразу показывает, где проблема — в кабеле, драйвере или питании.

### Код в чате
- AI пишет код с подробными комментариями.
- Пользователь сам переносит код в файлы и запускает.
- Exact patch (old/new блок) — только по явному запросу пользователя.

**Обоснование для TeamLead:** разработчик должен понимать каждую строку кода, которую он коммитит. Автоматическая правка файлов AI создает "черный ящик" в проекте.

### Mock-режим по умолчанию
- Любой новый софт должен работать без железа.
- Параметр `mock:=true` должен быть в launch-файлах.

**Обоснование для TeamLead:** CI/CD не может подключать реальные моторы или лидар. Без mock-режима автоматические тесты невозможны.

### Прогресс ежедневно
- Каждый день фиксировать результат в `docs/WEEKLY_LOGS.md`.

**Обоснование для TeamLead:** ежедневные логи дают прозрачность прогресса и помогают рано выявлять отклонения от плана.

### Коммиты и CI после каждого Issue
- После завершения каждого Issue делать коммит в GitHub.
- Коммит на русском языке в формате conventional commits:
  - `feat(weekN): краткое описание` — новая функциональность.
  - `fix(weekN): краткое описание` — исправление бага.
  - `docs(weekN): краткое описание` — изменение документации.
  - `refactor(weekN): краткое описание` — рефакторинг.
  - `test(weekN): краткое описание` — тесты.
- После push проверить CI в GitHub Actions: должен быть зелёный статус.
- Если CI падает — исправить перед переходом к следующему Issue.

**Обоснование для TeamLead:** мелкие атомарные коммиты + постоянно зелёный CI дают уверенность, что main-ветка всегда собирается. Большие коммиты в конце недели превращают merge в лотерею.

**Пример из практики:** на Week 3 изменения в CI накапливались локально и не проверялись до конца недели. В результате merge привёл к поломке pipeline. Если бы каждый Issue коммитился и проверялся отдельно, проблему нашли бы сразу.

## 4. Шаблон выдачи задачи

Для каждой задачи AI выдает:

1. **Цель и артефакт**
   - Что получится в результате.
   - Как проверить.

2. **Теория**
   - 1–2 абзаца: зачем это нужно и как работает.

3. **Пошаговое выполнение**
   - Конкретные действия.

4. **Команды проверки**
   - Терминальные команды и ожидаемый вывод.

5. **TL-проверка**
   - Что проверить.
   - Красные флаги.
   - Обоснование с точки зрения TeamLead.

**Обоснование для TeamLead:** единый формат задач позволяет новым членам команды быстро входить в процесс и не забывать про тестирование.

## 5. Версионирование документов

- ARCHITECTURE.md, PROTOCOL.md, SETUP.md и др. имеют секцию "История изменений".
- При любом изменении: инкремент минорной версии (v1.0 → v1.1), дата, автор, краткое описание.
- Новые ADR или изменения протокола — отдельные записи с обоснованием.

**Обоснование для TeamLead:** версионирование документов так же важно, как версионирование кода. Без него невозможно понять, когда и почему изменилось требование.

**Пример из практики:** изменение watchdog-таймаута с 200 мс на 500 мс должно быть задокументировано, иначе через месяц никто не вспомнит причину.

## 6. Завершение недели

1. **Финальный diff и тесты**
   - Пользователь показывает `git diff` и вывод `colcon test`.

2. **Code review AI**
   - Соответствие плану, архитектуре, протоколу.
   - Поиск багов и несостыковок.
   - Стиль и читаемость.

3. **Правки и коммиты**
   - `feat(weekN): ...`, `docs: ...`, `fix: ...`.

4. **Merge в `main`**
   - Через PR или локальный merge.
   - Чистая сборка `make clean && make build`.

5. **Обновление документов**
   - `docs/WEEKLY_LOGS.md`
   - `docs/SKILL_MATRIX.md`
   - `docs/PLAN_REVIEW_WN.md`

6. **Summary для центрального чата**
   - Что сделано.
   - Что не сделано и почему.
   - Уроки.
   - План на следующую неделю.

**Обоснование для TeamLead:** ритуал закрытия спринта превращает хаотичную разработку в предсказуемый процесс. Ретроспектива предотвращает повторение ошибок.

**Пример из практики:** `PLAN_REVIEW_W2.md` с фиксацией "всегда закладывать 30% buffer на hardware risks" — это знание, которое применяется во всех последующих неделях.

## 7. Команды быстрой проверки

```bash
cd ~/ROS2-AMR
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
ros2 launch amr_bringup bringup.launch.py
```

В другом терминале:

```bash
ros2 topic list
ros2 topic echo /cmd_vel
ros2 topic echo /odom
ros2 run tf2_tools view_frames.py
```
