# Корректировка плана: Week 2 → Week 3

## Контекст

Оригинальный план Week 2 предполагал закрытие 10 задач (Issue 1–10) за 5 дней при 4 часах/день. Фактически выполнено 3 задачи (Issue 1, 7, 8). Оставшиеся 7 задач переносятся в Week 3.

## Причины отклонения

### 1. Недооценка аппаратных рисков (главная)
- **План:** ESP32 прошивается за 1 день.
- **Факт:** Старый ESP32-WROOM-32 (внешний CP2102) не прошивается. Ошибка esptool: «Download mode detected, but TX path seems down». 3 дня потрачены на диагностику (кабели, GND, baud, boot-режим). Пытался настроить на ESP32F, тоже без успеха. Потраеного времени жаль.
- **Решение:** Заказан ESP32-DevKitC V4 (CP2102 на борту). Ожидается 20.06. Прошивка через встроенный USB-UART должна работать без танцев с бубном.

### 2. Переоценка скорости разработки
- **План:** 4 часов/дня хватит на 10 задач.
- **Факт:** срыв сроков из-за проблем с железом.
- **Решение:** необходимо закладывать допустимое время на каждую задачу и переходить к альтернативным решениям воибежании срыва дедлайнов.

### 3. Отсутствие backup-железа
- **План:** одна плата ESP32.
- **Факт:** Поломка/несовместимость одной платы = полная остановка потока.
- **Решение:** В Week 3 заказать 2-й ESP32 как spare (на будущее).


## TL-выводы

1. **Всегда закладывать 30% buffer на hardware risks.** В embedded интеграция занимает 3× больше времени, чем кажется.
2. **Mock-режим — must have.** Без него софтная команда простаивала бы 3 дня. С ним — 3 задачи закрыты параллельно с ожиданием железа.
3. **Прозрачность > красивый план.** Честный отчёт о 30% выполнении лучше, чем «всё по плану» с костылями.
